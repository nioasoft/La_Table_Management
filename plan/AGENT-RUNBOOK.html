קרא את זה לפני כל דבר אחר

DATABASE_URL ב-.env מצביע על פרודקשן. אין בפרויקט הזה בסיס נתונים לפיתוח. סוכן שרץ עם network_access=true יכול להגיע ל-Neon ולהריץ SQL הרסני, והוא יעשה את זה בביטחון מלא אם הוא יחשוב שזה עוזר.

האיסור מופיע בראש כל בריף וגם בצ'קליסט של הבודק, אבל האחריות היא של המפעיל: מיגרציות מורצות ביד, אחרי קריאה של ה-SQL. אף סוכן לא מריץ db:migrate.

מצב מבודד: worktree בלי .env

T01, T02 ו-T05 רצים ב-git worktree נפרד שאין בו .env. זו ההגנה היחידה כאן שאינה הצהרתית: בלי .env אין DATABASE_URL, והסוכן פיזית אינו יכול להגיע ל-Neon גם אם ישתכנע שזה עוזר.

שלושת אלה גם ממילא אינם צריכים DB, וגם הם השלושה הפנויים שבהם מתחילים. T03 ומעלה אינם יכולים לרוץ מבודדים: T03 קורא מה-DB ל-dry-run, ו-T04 ומעלה צריכים סכימה חיה. שם ההגנה חוזרת להיות האיסור בבריף ובצ'קליסט של הבודק.

הקמה

T=01-royalty-engine
MAIN="$PWD"
BR="agent/$T"
WT="$(dirname "$MAIN")/lt-wt-$T"

git worktree add -b "$BR" "$WT" HEAD
ln -s "$MAIN/node_modules" "$WT/node_modules"

# קבצי הלקוחה. raw_data/ ב-gitignore, ולכן התיקיות שלו לא נולדות ב-worktree.
mkdir -p "$WT/raw_data"

.env נמצא ב-.gitignore (שורה 15), ולכן worktree חדש נולד בלעדיו. זה לא טריק אלא תוצאה ישרה של איך שהפרויקט מוגדר.

raw_data/ גם הוא ב-.gitignore (שורה 70), וזו מלכודת אחרת לגמרי. חלק מהקבצים שם כן במעקב כי הם נוספו לפני שהכלל נכתב (82 קבצים, בהם BKMVDATA.txt ו-raw_files_suppliers/) — ולכן raw_data/ קיים ב-worktree, אבל התיקיות שאינן במעקב חסרות בו. ביניהן תמלוגים זכיינים/, כלומר בדיוק קבצי המקור של T01 ושל T05.

סוכן ב-worktree בלי ההעתקה הזאת ימצא raw_data/ קיים אבל בלי התיקייה שהבריף מפנה אליו, ואין לו שום דרך לדעת שזאת תקלת סביבה ולא מציאות. 120KB, מועתק ב-a-w כדי שלא יכתוב על נתוני הלקוחה.

ה-worktree יושב מחוץ ל-repo (../lt-wt-…), כדי שלא יופיע ב-git status של הראשי ולא יבלבל את הדיף.

node_modules הוא סימלינק ולא העתקה. 986MB, ואין סיבה לשכפל אותם.

הרצה במצב מבודד

codex exec -C "$WT" -s workspace-write \
  -c sandbox_workspace_write.network_access=true \
  -c model_reasoning_effort=high \
  --add-dir "$MAIN/node_modules" \
  --output-last-message "$RUN/last.md" \
  - < "$RUN/brief.md" > "$RUN/run.log" 2>&1

--add-dir "$MAIN/node_modules" אינו קוסמטי. הסימלינק מצביע אל מחוץ ל-workspace, ו-vitest כותב cache לתוך node_modules. בלי ההרשאה הכתיבה נחסמת, ההרצה יוצאת עם קוד 0, והסוכן מדווח בביטחון על בדיקות שלא רצו. זה בדיוק מצב "חסום-סנדבוק" שהשער בשלב 4 קיים כדי לתפוס.

הבדיקות רצות מתוך ה-worktree: cd "$WT" && npm test. אומת בפועל: 50 קבצים, 504 בדיקות, כולן עוברות בלי .env. אם בדיקה חדשה נכשלת שם על היעדר DB, זה ממצא אמיתי על טוהר הקוד ולא תקלת סביבה.

הבודק רץ גם הוא עם -C "$WT", אחרת הוא יסתכל על דיף ריק ב-repo הראשי ויאשר כלום.

מיזוג בחזרה וניקוי

# commit בתוך ה-worktree, אחרי שהבדיקות והבודק עברו.
# קבצים מפורשים ולא add -A: raw_data שהעתקת פנימה מוגן ב-gitignore, אבל אין סיבה להישען על זה.
cd "$WT" && git add <הקבצים בהיקף> && git commit -m "feat(royalty): <מה נבנה>"

# אם הראשי זז מאז שנוצר ה-worktree, ff-only יסרב. rebase של המשימה עליו, ואז ff.
cd "$WT" && git rebase master

# מיזוג לראשי. ff-only מכריח שהראשי לא זז מתחתינו.
cd "$MAIN" && git merge --ff-only "$BR"

# ניקוי. קודם הסימלינק, אחרת git מנסה למחוק 986MB.
rm -f "$WT/node_modules"

# ואז רק התיקייה שהעתקת. לא raw_data כולו — יש בו קבצים במעקב.
chmod -R u+w "$WT/raw_data/תמלוגים זכיינים" && rm -rf "$WT/raw_data/תמלוגים זכיינים"

git worktree remove "$WT" && git branch -d "$BR"

rm -f "$WT/node_modules" לפני worktree remove, בסדר הזה. ואם עבדת בתוך ה-worktree וה-shell עוד נמצא שם כשמוחקים אותו, כל פקודה אחריה נכשלת ב-Unable to read current working directory. cd "$MAIN" קודם, ואם זה קרה, git worktree prune מסדר את הרישום.

rm -rf "$WT/raw_data" מוחק 81 קבצים שכן במעקב, ואז worktree remove מסרב עם contains modified or untracked files. מוחקים את התיקייה שהעתקת בשמה, לא את ההורה.

ואם זה כבר קרה: הראשי הוא checkout נפרד ולא נפגע. אמת ב-git -C "$MAIN" status --porcelain (חייב להיות ריק) ורק אז git worktree remove --force. שים לב ש-git ls-files מחזיר שמות עבריים ב-escape אוקטלי, ולכן לופ אימות תמים על הפלט שלו ידווח על קבצים חסרים שכן קיימים. -z ו-read -d ''.

1הרכבת הבריף

הבריף של המיישם הוא _SHARED.md ואחריו קובץ המשימה. הם מודבקים, לא מועברים בנפרד:

לא מדביקים תוכן קבצים לתוך הבריף. הסוכן קורא את ה-repo בעצמו. הבריפים מפנים ל-plan/franchisee-royalty-billing-execution.html ול-raw_data/תמלוגים זכיינים/, וזה מכוון.

2המיישם
codex exec -C "$PWD" -s workspace-write \
  -c sandbox_workspace_write.network_access=true \
  -c model_reasoning_effort=high \
  --output-last-message "$RUN/last.md" \

הרץ עם run_in_background: true והמשך לעבוד. ההארנס מודיע בסיום.

network_access=true הוא חובה ולא נוחות. -s workspace-write חשוף חוסם את כל הרשת, כולל localhost ו-unix sockets. סוכן שלא מצליח להריץ npm לא נכשל ברעש. הוא מתדרדר בשקט להסקה ומחזיר דוח משוכנע ומקולקל. זו הדרך המרכזית שבה הרצאות כאלה מתבזבזות.

model_reasoning_effort=high על T01, T06, T08 ו-T09. השאר יכולים בברירת מחדל.

3תפיסת ה-session id, לפני שהבודק רץ
IMPL_SID=$(find ~/.codex/sessions -name '*.jsonl' | sort | tail -1 \
  | sed -E 's/.*-([0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12})\.jsonl$/\1/')
echo "$IMPL_SID" | tee "$RUN/impl.sid"

זה השלב שקל לדלג עליו וזה שובר את הלופ. ההרצה של הבודק יוצרת session חדש באותו cwd, ומאותו רגע codex exec resume --last מחזיר את הבודק ולא את המיישם. הממצאים יגיעו לסוכן שאין לו את הקוד בהקשר, והוא יתחיל לנחש. תופסים את ה-id לפני, ומשתמשים בו במפורש.

ה-id מוטבע בשם קובץ ה-session: rollout-<timestamp>-<uuid>.jsonl. אומת בפועל שגם החילוץ וגם resume לפי id מפורש שומרים הקשר.

ואם דילגת בכל זאת — זה לא אל-חזור. שני ה-sessions נבדלים בתוכן, ואפשר לסמן אותם לפי חתימה:

for f in $(ls -t $(find ~/.codex/sessions -name '*.jsonl' -newermt '<לפני ההרצה>')); do
  sid=$(echo "$f" | sed -E 's/.*-([0-9a-f-]{36})\.jsonl$/\1/')
  role="?"
  grep -q '<כותרת הבריף, למשל: T01 — מנוע החישוב>' "$f" && role="IMPL"
  grep -q 'אל תוסיף מידע על מה שהסוכן הראשון' "$f" && role="REVIEW"
  echo "$role  $sid"
done

המחרוזת השנייה היא מ-_REVIEW-TEMPLATE.md ומופיעה רק בסשן של הבודק. עלות השחזור היא קריאה אחת, אבל זה עדיין זול יותר לתפוס את ה-id מראש.

7Claude מכריע

קרא את review.md ואת הדיף. אל תקבל את ממצאי הבודק כנתון. סוכן בודק ממציא ממצאים כדי למלא רשימה, ומצד שני מפספס דברים. תפקידך להכריע איזה ממצא אמיתי ואיזה לא, ולהוסיף מה שאף אחד מהשניים לא ראה.

בנוסף לרשימה שלו, עבור בעצמך על:

  • git status --porcelain: קבצים מחוץ להיקף, וקבצים זמניים שנשארו.
  • מסלול הכסף: עיגול, כיוון ההנחה, בסיס הרף.

אין ממצאים חוסמים → שלב 9. יש → שלב 8.

8חזרה למיישם, לפי id מפורש

כתוב ל-$RUN/fix.md את הממצאים שהכרעת שהם אמיתיים, ממוספרים, כל אחד עם קובץ:שורה ומה הנכון. בלי "הבודק אמר ש". אתה מזמין את התיקון.

# במצב מבודד: cd "$WT". אחרת cd "$MAIN".
cd "$WT" && codex exec resume "$(cat "$RUN/impl.sid")" \
  -c sandbox_mode="workspace-write" \
  -c sandbox_workspace_write.network_access=true \
  -c sandbox_workspace_write.writable_roots="[\"$MAIN/node_modules\"]" \
  -o "$RUN/last-r2.md" \
  - < "$RUN/fix.md" > "$RUN/run-r2.log" 2>&1

codex exec resume מקבל קבוצת דגלים אחרת מ-codex exec. יש לו -c, -o, -m, --last — ואין לו -C, -s או --add-dir. כל אחד מהשלושה מפיל את הפקודה על פירוק ארגומנטים לפני שהסוכן מקבל את הבריף, וההודעה יושבת רק ב-run-r2.log.

לכן: את ה-cwd קובעים ב-cd, את הסנדבוק ב--c sandbox_mode, ואת ההרשאה ל-node_modules ב--c sandbox_workspace_write.writable_roots. זה השקול ל---add-dir משלב 2, ובלעדיו vitest נחסם בשקט בכתיבת cache — אותה מלכודת, שם אחר.

לא לתקן בעצמך. תיקון ב-Claude מייבא בחזרה בדיוק את העלות שהעברנו.

ב-resume, קוד יציאה 0 אינו אומר שהסבב קרה. דגל שגוי גורם ל-Codex לצאת 0 כשהשגיאה יושבת רק ב-run-r2.log. אמת שהעץ זז — git status ו-wc -l על קבצי ההיקף לפני ואחרי — ואם לא, tail -5 "$RUN/run-r2.log". הרצה שנפלה על דגלים אינה נספרת כסבב: הסוכן לא ראה את הבריף.

מקסימום שני סבבים. אחרי שניים, אם עוד יש ממצא חוסם, זה סימן שהבריף לא היה מדויק ולא שהסוכן חלש. תקן את הבריף והתחל את המשימה מאפס. אחרי שלב 8 חוזרים ל-4.
