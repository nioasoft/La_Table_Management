תיקון תהליך העלאת דוחות ספקים — רבעון, עיתוי ושגיאות

נכתב 30/06/2026 · נובע מכשלי העלאה של אראל אריזות ופרסקו (אורי פרסקו)

למה אנחנו עושים את זה (הקשר)

שני ספקים דיווחו "לא הצלחתי להעלות" דרך קישור ההעלאה העצמית. החקירה חשפה שלוש בעיות נפרדות:

  1. אראל אריזות — קובץ .xls ישן נדחה בולידציית magic-bytes (FILE_TYPE_MISMATCH). תוקן ונפרס מקבל cfb ל-.xls/.doc ישנים.
  2. פרסקו — הקובץ עלה ונקרא בהצלחה, אבל נחתם כרבעון 1 במקום רבעון 2 → נדחה ככפילות (409) מול קובץ Q1 קיים. זו הבעיה המרכזית כאן.
  3. שגיאות עמומות + עיוורון — השגיאות שמופיעות לספק לא מסבירות מה לעשות, ורוב הדחיות אינן נרשמות בשרת, אז אנחנו לא יודעים מה קרה בלי לחפור ב-Vercel ידנית.

שורש הבעיה — למה פרסקו נחתם כ-Q1 (מאומת)

התקופה של קובץ העלאה נגזרת כך ב-src/app/api/public/upload/[token]/route.ts (שורות 680–702):

  • אם יש תאריכים בשורות הקובץ → לוקחים מוקדם..מאוחר.
  • אם אין תאריכים (פרסקו, נספרסו, אראל — ה-parser מחזיר date: null) → fallback שמחשב תקופה מהתאריך הנוכחי: getPeriodsForFrequency(quarterly, new Date(), 1, includeCurrent=false).

החישוב ב-30/06/2026: includeCurrent=false מדלג על הרבעון הנוכחי (Q2) ומחזיר את הרבעון המלא האחרון = Q1 (01/01–31/03). מכאן חותמת ה-Q1.

אי-העקביות שגרמה לכל הסיפור

לוגיקת רבעוןתוצאה ב-30/6
בקשת הדוח (cron)includeCurrent=true"Q2 נסגר היום" → שולח בקשת Q2
חותמת ההעלאה (קובץ בלי תאריכים)includeCurrent=false"רבעון מלא אחרון" → חותם Q1

הבקשה אומרת Q2, ההעלאה חותמת Q1 → דחיית כפילות. אם הבקשה הייתה יוצאת ב-1/7 (כפי שביקש אסף), ההעלאה הייתה ביולי → "רבעון מלא אחרון" = Q2 → הכל עובד. שני הדברים הם אותו שורש.

Workstream 1 — לחתום תקופה לפי הבקשה (משחרר את פרסקו היום)

דחיפות גבוהה

קובץ: src/app/api/public/upload/[token]/route.ts (אזור שורות 685–702).

הרעיון: הקישור מקושר ל-file_request דרך file_request.upload_link_id = link.id, ובמטא-דאטה שלו נשמר periodKey: "2026-Q2" (אומת ב-DB). נשתמש בזה במקום לנחש מתאריך ההעלאה.

סדר עדיפויות חדש לקביעת התקופה

  1. תאריכים בתוך הקובץ (כמו היום) — מנצח כשקיימים.
  2. חדש: periodKey מה-file_request של הקישור → המרה לתאריכים עם getPeriodByKey(periodKey) (כבר קיים ב-settlement-periods.ts:252).
  3. fallback הקיים מבוסס-תאריך — רק אם אין בקשה משויכת.
// בתוך הענף "אין תאריכים בקובץ" (היום שורות 693–701):
// 1) קודם ננסה את התקופה שהתבקשה דרך הקישור
const fileReq = await getFileRequestByUploadLinkId(link.id); // helper חדש קטן
const requestedKey = (fileReq?.metadata as Record<string,unknown> | null)?.periodKey as string | undefined;
const requestedPeriod = requestedKey ? getPeriodByKey(requestedKey) : null;

if (requestedPeriod) {
  periodStartDate = formatDateAsLocal(requestedPeriod.startDate);
  periodEndDate   = formatDateAsLocal(requestedPeriod.endDate);
} else {
  // 2) fallback מבוסס-תאריך הקיים (ללא שינוי)
  const frequency = (supplier.settlementFrequency as SettlementPeriodType) || "quarterly";
  const periods = getPeriodsForFrequency(frequency, new Date(), 1, supplier.fiscalYearStartMonth ?? 1);
  if (periods.length > 0) { /* ... כמו היום ... */ }
}
  • helper חדש getFileRequestByUploadLinkId(linkId) ב-src/data-access/fileRequests.ts (כבר יש שם שאילתות לפי uploadLinkId — רק getter שמחזיר את ה-row + metadata).
  • תוצאה לפרסקו היום: קובץ בלי תאריכים → periodKey "2026-Q2" → נחתם Q2 → אין כפילות מול ה-Q1 הקיים → עובר.
  • בונוס: עמיד גם למי שמעלה באיחור (אוקטובר) — עדיין ייחתם לפי התקופה שהתבקשה, לא לפי תאריך ההעלאה.

(ב) קוד-שגיאה גלוי לספק

בתיבת השגיאה האדומה (page.tsx שורות 508–515) להוסיף שורה קטנה: קוד: FILE_TYPE_MISMATCH. כך הספק יכול לצלם/להקריא לנו את הקוד ואנחנו יודעים מיד מה קרה — בלי לחפור בלוגים.

(ג) רישום אחיד בשרת לכל דחייה

היום רק FILE_TYPE_MISMATCH כותב console.warn; שאר ה-4xx שקטים. נוסיף console.warn("upload rejected", {code, status, supplierName, linkId, email, fileName}) בכל החזרת שגיאה ב-route. כך כל דחייה ניתנת לחיפוש דרך Vercel logs לפי קוד/ספק.

ponytail: לא בונים טבלת DB/דשבורד לדחיות עכשיו — console.warn אחיד + שאילתת Vercel logs מספיק. אם נצטרך מעקב מתמשך, נוסיף persist בהמשך.

אימות (end-to-end)

  • WS1: בנייה (npm run build). אחרי deploy — לבקש מפרסקו להעלות שוב את אותו קובץ דרך הקישור; אמור לעבור (נחתם Q2). לאמת ב-DB שנוצר uploaded_file + תקופה Q2.
  • WS2: להריץ את ה-cron עם ?date=2026-07-01&dryRun=true ולוודא שמחזיר Q2; ועם ?date=2026-06-30&dryRun=true שלא שולח כלום חדש (Q1 כבר נשלח).
  • WS3: להעלות קובץ פגום/סוג לא נכון ולראות את ההודעה החדשה + הקוד; לאמת console.warn ב-Vercel logs.
